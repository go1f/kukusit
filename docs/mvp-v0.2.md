# 坐姿诊断 MVP v0.2

日期：2026-10-09。应用：`dist/PostureDiagnostics.app`。这是已能实拍运行的原生 macOS 诊断版，当前不发送坐姿提醒。

## 1. 使用方式

1. 打开应用，点击“开始观察”。第一次使用时，由 macOS 请求摄像头权限。应用只选择内置摄像头，不使用麦克风。
2. 看预览里的脸框、脸部点与双肩点，确认完整脸部、双肩和部分上胸可见。绿色与橙色表示点的质量状态；右侧文字表示对应指标是否真正可判定。
3. 默认肩部模型为 MediaPipe Pose；可以切回 Apple Vision 做对照。切换模型会暂停观察，避免混合不同后端的数据与参考。
4. 选择“上方外接屏”，在自己选定的舒适姿态下看屏幕中心，点击“开始 20 秒校准”。经常看笔记本时，可再保存下屏参考。校准期间不必直视摄像头。
5. 校准成功后，头部倾斜和肩线显示相对参考的偏移。如果双肩在校准期间不够稳定，允许仅保存头部参考；不会补出肩部基线。姿态波动过大或有效观察不足时，拒绝保存。
6. 点击“暂停观察”停止采集并清空预览。关闭诊断窗口、锁屏／系统休眠信号也会暂停；恢复后需要手动开始。
7. “导出数值摘要”保存 JSON 聚合数据，包含已分析帧数、可用率、观察时间、分析率与近期管线耗时，不含照片、录像或逐帧关键点。

演示模式不占用摄像头，也不能保存个人校准。它提供正常覆盖、肩部出画和多个目标三个合成情境，便于检查界面与降级逻辑。镜像只影响预览，人体左右标签与特征计算保持一致。

关闭窗口后，菜单栏入口仍保留。在应用激活时按 `⌘⇧D` 可重新打开诊断窗口；重开时保持暂停，参考仍在，不自动恢复摄像头。

## 2. 已实现内容

| 部分 | 实现 |
|---|---|
| 原生界面 | SwiftUI 诊断窗口、菜单栏入口、预览与关键点叠加、状态与性能卡片 |
| 摄像头 | AVFoundation 内置设备选择、720p 输出、支持时请求 15 FPS、约 6 Hz 分析 |
| 人脸 | Apple Vision 脸框、脸部关键点与可选 roll／yaw／pitch |
| 肩部 | Apple Vision 对照后端，以及本地 MediaPipe Pose Full 后端 |
| 坐标适配 | MediaPipe 上左原点转为统一的下左原点；人体左右保持；像素尺度计算肩线 |
| 质量 | 多目标、关键点边界、置信度、脸肩目标关联、大幅侧转、过期观察与后端错误处理 |
| 校准 | 20 秒稳定观察，中位数／MAD＋90 分位偏移检查；有效时间累计排除缺失与重复时间戳 |
| 存储 | 在 Application Support 中原子写入观看情境参考；不自动漂移基线 |
| 生命周期 | 用户暂停、退出、系统睡眠／会话变化、采集错误、中断；旧任务结果不会重新显示 |
| 本机助手 | 有界最新结果槽；单个管道请求；超时／取消；暂停和退出会终止助手 |

## 3. 实拍驱动的架构调整

v0.1 首选纯 Apple Vision，优点是原生依赖少。实际试验显示，该机位下的原生身体请求没有给出可用双肩；使用者确认双肩和部分上胸完整出现在预览中。因此，当前版本采用 **Apple Vision 人脸＋MediaPipe Pose 肩部**，保留纯原生方案作为界面对照项。

MediaPipe Tasks 官方支持视频帧和归一化关键点输出；本实现使用 VIDEO 模式，时间戳单调递增，按每个点的 visibility 与 presence 的较低值处理质量，不把模型预测深度当作真实测量。[官方 Pose 说明](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker) · [Python 接口](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/python)

后端通过私有进程管道接收内存中的 BGRA 帧；仅将二维关键点数值返回原生应用。没有视频文件、网络监听或云端推理。当前采用 Python 助手加快模型对照，后续可将相同适配接口替换为原生推理组件。

环境锁定为 MediaPipe 0.10.35、NumPy 2.2.6、Python 3.12.14。Pose Full 模型使用官方版本 1，SHA-256 为 `5134a3aad27a58b93da0088d431f366da362b44e3ccfbe3462b3827a839011b1`。[版本来源](https://pypi.org/project/mediapipe/0.10.35/)

## 4. 验证范围

- 25 项原生核心检查已通过：非正方形图像角度、镜像／留黑变换、角度环绕、缺失值、多目标、边缘点、目标关联、校准稳定性、丢帧／重复时间戳、采样相位、JSON 往返、MediaPipe 坐标与低质量点适配、肩部失败时保留人脸。
- Swift → Python → MediaPipe 的实际进程管道检查已通过：两张合成空白 BGRA 帧返回零人体；取消后拒绝进一步发送帧。该检查不申请摄像头权限。
- 本机原生实拍导出：4,289 个已分析帧，脸部可用率约 99.93%，双肩可用率 0%；720p 已核对。原生界面短时 p95 约 38–58ms，导出记录为近期 58.25ms。
- MediaPipe 最终实拍导出：约 8.55 分钟、3,067 个已分析帧，脸部可用率 99.67%、双肩可用率 99.02%，近期分析率 6.00 Hz、管线 p95 61.92ms。证据见 `validation/mediapipe-live-2026-10-09.json`。
- 原生界面已经检查暂停清空画面、合成预览叠加、肩部出画降级、多目标全部未知、演示禁用校准，以及数值摘要的保存流程。
- 最终构建已验证关闭诊断窗口后停止观察，再用 `⌘⇧D` 重开：保持暂停、角度全为不可用、当前分析率为 0、个人参考保留，进程检查确认没有残留 Pose 助手。证据见 `validation/lifecycle-2026-10-09.json`。

以上可用率指“已分析帧通过质量规则的比例”，不是关键点位置或坐姿分类的准确率。原生与 MediaPipe 的观测时段长度不同，使用者也可能移动，当前对照适合选择实现路线，不能当作严格控制的性能论文结果。

原生首轮 JSON 的 elapsedSeconds 在保存对话框期间未刷新；后续实现已改为导出时直接读取单调时钟。原始报告保留原样，原生结果主要依据帧数与有效帧比例，不用该时间字段计算平均帧率。

资源记录为一次 `ps` 抽样：原生应用 RSS 约 241.62MiB、助手约 199MiB，两项 CPU 数值合计约 50.8%（一个逻辑核为 100%）。RSS 直接相加约 440.62MiB，可能重复计算共享页，但仍提示原定单进程 300MB 的预算需要重新验证与优化。不是长时耗电测试；尚未完成 20 分钟关闭／仅采集／完整推理的控制实验，也尚未测试所有光照、全屏与显示器拔插情境。

使用者已在真实摄像头下成功保存“上方外接屏”的头部与肩线参考，界面正确显示相对参考偏移。个人参考文件保留在 Application Support，不复制到项目验证记录中。
